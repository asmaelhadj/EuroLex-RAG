# ADR 007: Evaluation harness

- Status: accepted
- Date: 2026-10-25

## Metrics (article level)

Each retrieved chunk maps to its article id (`gdpr:art-6`); recital chunks map to nothing.

- **recall@k** = |gold ∩ article ids in the top k chunks| / |gold|, for k = 1, 3, 5, 10.
- **MRR** = 1 / rank of the first chunk whose article is gold (0 if none in the top 10).
- **nDCG@10** with binary relevance. Only the first chunk of each article can earn gain, so
  retrieving three paragraphs of the same article does not count three times. The ideal list
  has min(|gold|, 10) relevant items.
- Recital chunks still take a rank. The metric asks "did we find the article?", and a recital
  in slot 1 pushes the article down.
- Out-of-scope questions are excluded from retrieval metrics. Their top retrieval score is
  saved for the refusal threshold in Phase 5.

## Question set workflow

1. `candidates.py` asks an LLM (`CANDIDATE_MODEL`, refused if it equals `LLM_MODEL`) for
   questions per article, false-premise questions, multi-article questions built from real
   cross-references (e.g. Art. 17 -> Art. 6), and out-of-scope questions. Every row is
   `source: llm_candidate`, `status: pending`, and `notes` records the model and source
   articles. Near-duplicates are skipped.
2. `review_cli.py review` shows each pending question with its gold article text. The
   reviewer validates, rejects or edits it. Every decision goes to `data/eval/review_log.jsonl`
   (no personal data), which gives the candidate rejection rate for the README.
3. `review_cli.py add` adds human-written or FAQ questions as validated.
4. `review_cli.py split` sets dev/test (default 80/20) from a hash of the question id and a
   seed. A question's split never changes when others are added, so a test question cannot
   drift into dev after tuning.

## Runs

`make eval CONFIG=... SPLIT=...` saves `runs/<run_id>/results.json` (per-question chunks,
scores, metrics, latency) and `summary.json` (no per-question data; the only file committed).
Each run records the experiment and embedding configs, git commit and dirty flag, seed,
torch/GPU, and a SHA-256 of the exact questions used.

A run is **not reportable** if it includes pending questions (`--include-pending`) or a
`--limit`. `make report` ignores those runs and writes `TODO` where no reportable run exists.
It shows the latest reportable run per experiment and split, with a separate row for the
human/FAQ core (SPEC.md section 7). It also warns if runs on one split used different
question sets.

## Smoke test (2026-10-25)

14 candidates generated by `mistral:latest` from 4 articles. Two of the three "out of scope"
candidates were in fact covered by the GDPR (territorial scope, transfers), so generated
labels cannot be trusted without review.
